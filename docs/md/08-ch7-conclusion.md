## บทที่ 7 สรุป ปัญหา และข้อเสนอแนะ

### 7.1 สรุปผล

คณะผู้จัดทำติดตั้ง WordPress บนเซิร์ฟเวอร์คลาวด์ด้วยตนเองครบทั้ง 3 ขั้นตามโจทย์ เว็บไซต์เข้าถึงได้ที่ https://elephotelephus.site ผ่าน HTTPS, SSH ใช้กุญแจเท่านั้นและปิด root, geo-firewall รับเฉพาะ IP ไทย 1,167 ช่วง และจุดทดสอบจากต่างประเทศที่เลือกใช้ทุกจุดเชื่อมต่อไม่ได้ในเวลาทดสอบ และเว็บไซต์ประชาสัมพันธ์สาขาใช้งานได้จริงพร้อมข่าวจากคณะที่อัปเดตเอง การตรวจเพิ่มเติมหลังปรับตัวเก็บข้อมูล (หัวข้อ 6.4) ยืนยันว่ายอดคำขอ HTTP 1,818 ครั้งตรงกับผลรวมสถานะ HTTP และการนำเข้าข่าวซ้ำสองรอบไม่สร้างโพสต์ซ้ำ (111 → 111 → 111 โพสต์ ภาคผนวก ง) ผลเทียบกับวัตถุประสงค์ทั้ง 6 ข้อในหัวข้อ 1.2 สรุปในตารางที่ 7.1

ตารางที่ 7.1 ผลการดำเนินงานเทียบกับวัตถุประสงค์

| วัตถุประสงค์ | ผล | หลักฐาน |
| --- | --- | --- |
| 1. ติดตั้ง nginx, PHP, MySQL และ WordPress บนคลาวด์ด้วยตนเอง | บรรลุ ติดตั้งด้วย setup.sh บน Google Compute Engine | ตารางที่ 3.1, ภาพที่ 3.2 |
| 2. เข้าถึงเว็บไซต์ผ่านโดเมนด้วย HTTPS | บรรลุ ใบรับรอง Let’s Encrypt แบบ DNS-01, TLS 1.3, ส่งต่อ HTTP ไป HTTPS | ภาพที่ 4.1 |
| 3. SSH ปิด root ปิดรหัสผ่าน ใช้กุญแจเท่านั้น | บรรลุ | ภาพที่ 4.2–4.3 |
| 4. firewall รับเฉพาะ IP ไทย | บรรลุสำหรับ IPv4 ส่วน IPv6 ปิดพอร์ตบริการทั้งหมด ข้อจำกัดคือกันผู้ใช้ VPN ไทยไม่ได้ | ภาพที่ 4.5, 6.1–6.2 |
| 5. เว็บไซต์ประชาสัมพันธ์สาขาสำหรับนักเรียนมัธยม | บรรลุ ธีมเขียนเอง แก้เนื้อหาได้จากหลังบ้าน นำเข้าข่าวคณะอัตโนมัติโดยไม่สร้างข่าวซ้ำ | ภาพที่ 4.6–4.10, ภาคผนวก ง |
| 6. ระบบตรวจจับจาก log พร้อม dashboard และ AI | บรรลุ อ่าน log 4 แหล่ง แสดงผลในหลังบ้าน และสรุปด้วย Gemini ทุกชั่วโมง ข้อจำกัดคือตรวจตามกฎที่กำหนดไว้ | ภาพที่ 6.3–6.6, หัวข้อ 6.4 |

ส่วนเพิ่มเติมคือระบบ secdash ที่ทำให้เห็นการโจมตีที่เกิดขึ้นจริง เช่น บอทสแกนไฟล์ลับและการไล่หาชื่อผู้ใช้ และใช้ AI สรุปเป็นภาษาไทยทุกชั่วโมง บทเรียนสำคัญคือการป้องกันหลายชั้นทำให้ชั้นหนึ่งที่พลาดไม่กลายเป็นความเสียหาย และคำแนะนำจาก AI ต้องตรวจกับระบบจริงก่อนนำไปใช้

### 7.2 ปัญหาและแนวทางแก้ไข

ตารางที่ 7.2 ปัญหาที่พบระหว่างทำโครงงาน

| ปัญหา | สาเหตุ | วิธีแก้ |
| --- | --- | --- |
| setup.sh หยุดทำงานเงียบๆ หลังใส่ Zone ID | ฟังก์ชันสุ่มรหัสผ่านใช้ pipe ที่เกิด SIGPIPE เมื่อเปิด set -e | อ่านจาก /dev/urandom เป็นก้อนขนาดคงที่แทน และตรวจ token กับ Cloudflare ก่อนทำต่อ |
| ตั้งค่าภาษา WordPress ไม่สำเร็จ | ไม่พบไฟล์ภาษา th ในขั้นติดตั้ง | ติดตั้งเป็น en\_US แล้วเปลี่ยนภาษาภายหลังในหน้าตั้งค่า |
| wp-cli สร้าง rewrite rule ไม่ได้ | สิทธิ์ไดเรกทอรีทำงานไม่ตรงกับผู้ใช้ www-data | เรียก wp-cli เป็น www-data ในโฟลเดอร์เว็บ และไม่ใช้ --hard |
| เว็บตอบ NXDOMAIN | มี A record เฉพาะ cs ยังไม่มี @ | เพิ่ม A record ของ @ และล้าง DNS cache |
| แหล่ง IP ไทย (ipdeny) ส่งรายการว่าง | ดาวน์โหลดไม่สำเร็จ สคริปต์จึงไม่ยอมเปิด firewall | เปลี่ยนไปใช้ไฟล์สถิติของ APNIC และเก็บ ipdeny เป็นแหล่งสำรอง |
| สคริปต์หา IP ของผู้ดูแลไม่เจอ | sudo ลบตัวแปร SSH\_CLIENT | ใช้ค่าสำรองจาก who -m |
| ขั้น 2FA ถูกนับเป็น login ผิด | หน้า 2FA ตอบ 200 เหมือนรหัสผิด | ตัดออกเมื่อ 2FA สำเร็จตามมาใน 5 นาที |
| IP ของทีมถูกนับเป็นผู้โจมตี | ตัวแก้ไขบทความเรียก API รายชื่อผู้ใช้ | IP ที่ login สำเร็จถือเป็นคนในทีม |
| เรียก AI ไม่สำเร็จ (404, 503, timeout) | โมเดลเดิมถูกปลด เซิร์ฟเวอร์ AI ไม่ว่าง และรุ่นใหม่ตอบช้า | เลือกรุ่นอัตโนมัติ รอนานขึ้น และสลับรุ่นเมื่อมีปัญหา |
| DBeaver ต่อฐานข้อมูลไม่ได้ | ตั้งให้ต่อตรงพอร์ต 3306 ซึ่งไม่ได้เปิด | ใช้ SSH tunnel และตั้ง allowPublicKeyRetrieval |
| ไฟล์ WordPress core ไม่ตรงต้นฉบับ (php-ai-client) | WordPress อัปเดตตัวเองจาก 7.1.3 เป็น 7.1.4 ไม่ครบ ไฟล์สองเวอร์ชันปนกัน | ตรวจว่าไม่มีโค้ดอันตราย แล้วดาวน์โหลด core เวอร์ชันเดิมทับใหม่ (wp core download --force --skip-content) ผลตรวจผ่าน |
| geo-firewall ปิดโดยไม่ตั้งใจ | สั่ง apply ใหม่แต่ไม่ได้ confirm ภายใน 3 นาที ระบบย้อนกลับเอง | ตรวจพบจาก security-check.sh แล้วเปิดใหม่ทันที |
| firewall บล็อก IP ของเซิร์ฟเวอร์เอง | WordPress เรียกตัวเองผ่านโดเมน ซึ่งวนกลับมาด้วย IP สาธารณะของเครื่อง | geo-firewall อ่าน IP ของเครื่องจาก metadata ของ Google Cloud แล้วอนุญาตอัตโนมัติ |
| dashboard ไม่เห็น log ของ SSH และ firewall | systemd บน Ubuntu 24.04 พิมพ์เวลาแบบ +07:00 แต่ตัวเก็บข้อมูลรองรับแค่ +0700 | แก้ให้อ่านเวลาได้ทั้งสองแบบ หลังแก้เห็น SSH ล้มเหลว 212 ครั้งและ IP ต่างประเทศ 691 IP |

### 7.3 ข้อจำกัด

- geo-firewall กันผู้โจมตีที่ใช้ IP ไทย (VPN ไทย หรือเครื่องในไทย) ไม่ได้ จึงต้องพึ่งชั้นอื่นด้วย
- คนไทยที่อยู่ต่างประเทศและบริการตรวจเว็บจากต่างประเทศ (เช่น SSL Labs) เข้าเว็บไม่ได้
- การจัดประเภทการโจมตีใช้รูปแบบที่กำหนดไว้ การโจมตีแบบใหม่อาจไม่ถูกตรวจพบ และยังไม่ได้วัดอัตราการตรวจพบหรือการแจ้งเตือนผิดด้วยชุดข้อมูลทดสอบที่รู้คำตอบ
- จำนวน IP ต่างประเทศที่ถูกบล็อกนับจาก log ที่จำกัดอัตราการบันทึก จึงเป็นจำนวนขั้นต่ำ
- การถือว่า IP ที่ล็อกอินสำเร็จเป็นคนในทีม อาจซ่อนเหตุการณ์บางประเภทจากผู้อื่นที่ใช้ IP ร่วมกัน
- การทดสอบจากต่างประเทศใช้จุดทดสอบของ check-host.net ในเวลาหนึ่ง ไม่ได้ครอบคลุมทุกเครือข่ายทั่วโลก
- เซิร์ฟเวอร์มีเครื่องเดียว ถ้าเครื่องล่มเว็บจะหยุดให้บริการ

### 7.4 ข้อเสนอแนะ

1. ติดตามแพตช์ถาวรของ CVE-2026-115560 แล้วอัปเดต PHP ทันทีที่ออก และรัน security-check.sh เป็นประจำ
2. ใช้ reverse proxy หรือ cache ของ Cloudflare เพื่อเพิ่มความเร็วและซ่อน IP จริง โดยย้ายการกรองประเทศไปไว้ที่ Cloudflare
3. ส่งแจ้งเตือนทันที (เช่น อีเมลหรือ LINE) เมื่อระดับความเสี่ยงเป็น “สูง”
4. เก็บไฟล์สำรองไว้นอกเซิร์ฟเวอร์ เช่น Cloud Storage กันกรณีเครื่องเสียหายทั้งเครื่อง
5. เพิ่ม Web Application Firewall เช่น ModSecurity กับชุดกฎ OWASP CRS
